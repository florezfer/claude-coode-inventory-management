Factory Inventory Management System

A Vue 3 single-page app backed by a FastAPI service that reads static JSON into memory. No database, no build-time data, no persistence — every request filters in-process over lists loaded at import.

Vue 3 + Vite 8 · :3000 FastAPI · :8001 19 endpoints · 17 GET, 2 POST 8 views · 9 components 32 inventory items · 250 orders 97 backend tests

System architecture

Two processes, started together by scripts/start.sh. The Vite dev server and the API are entirely separate; the browser talks to each directly, which is why the backend enables permissive CORS.

Request & data flow

One round trip, from a user changing a filter to repainted pixels.

  1. User changes a filter in FilterBar.vue

    Writes to a ref in useFilters.js. Those four refs are declared at module scope, outside the exported function — so every component shares one singleton state rather than its own copy.

  2. Views react via watch

    No props are threaded through. Each view watches the four refs directly and re-fetches when any changes.

  3. getCurrentFilters() renames fields

    selectedLocation → warehouse, selectedPeriod → month. Any value of 'all' is dropped rather than sent.

  4. api.js builds the query string

    A single axios module is the only place the API base URL should appear.

  5. FastAPI filters in-process

    apply_filters() matches warehouse exactly and category/status case-insensitively. filter_by_month() matches a YYYY-MM substring, or expands Q1-2025 through QUARTER_MAP.

  6. Pydantic validates the response

    Declared by response_model, so a drifting JSON shape fails loudly at the boundary instead of silently reaching the UI.

  7. Vue stores raw data in refs, derives the rest

    Totals, groupings and chart series are computed — cached until a dependency changes, never recomputed per render.

The filter system

Four global filters drive nearly every screen. The important asymmetry: they are not applied uniformly.

Time Period → month

orders · dashboard only

  • filter_by_month() reads only the order_date field
  • Inventory has no time dimension, so it silently ignores this filter
  • Accepts YYYY-MM or Q#-YYYY

Location → warehouse

San Francisco · London · Tokyo

  • Exact string match, case-sensitive
  • Applies to inventory and orders

Category

5 values

  • Circuit Boards, Sensors, Actuators, Controllers, Power Supplies
  • Case-insensitive match

Order Status

orders only

  • Processing, Shipped, Delivered, Backordered
  • Dashboard counts Processing + Backordered as “pending”

Cross-cutting: i18n and currency

A second module-scope singleton, useI18n.js, persisting locale to localStorage['app-locale'].

Currency follows locale

  • Not an independent setting: ja ⇒ JPY, everything else ⇒ USD
  • utils/currency.js converts with a hardcoded USD_TO_JPY = 150
  • Stored values are always USD; conversion is display-only

Data values are translated too

  • translateProductName, translateCustomerName, translateWarehouse
  • Warehouse mapping rewrites city names and the Warehouse X-## prefix
  • New products, customers or warehouses need locales/ja.js entries or they render untranslated

Gaps worth knowing before you build

Verified against the source, not inherited from the docs.

Four client API methods have no backend route

api.js calls /api/tasks (get, create, delete, toggle). None exist in main.py, so all four 404 at runtime. TasksModal.vue — 621 lines, wired into App.vue — calls them.

Restocking joins the forecast to inventory

The Restocking tab ranks forecast items by forecasted_demand − quantity_on_hand and funds them greedily within a budget. That join is only possible because demand_forecasts.json was re-skued onto real inventory SKUs — the two files previously shared just one SKU, which silently collapsed the Demand tab to a single row under any filter. test_demand_forecast_skus_exist_in_inventory now guards it.

Purchase orders have routes but no UI

POST /api/purchase-orders and GET /api/purchase-orders/{backlog_item_id} are implemented and tested, enforcing one purchase order per backlog item (409 on a second). The matching api.js methods still aren't called by any component — wiring BacklogDetailModal.vue to them is the remaining work.

Created purchase orders don't survive a restart

They're appended to the in-memory purchase_orders list, never written back to purchase_orders.json. That matches the rest of the data layer, but it also means the list is shared global state — conftest.py carries an autouse fixture that restores it around each test.

Reports.vue bypasses the API layer

It imports axios directly and hardcodes http://localhost:8001 twice, rather than going through api.js like every other view. Changing the API base URL would miss it.

Backlog.vue is orphaned

Absent from the router and imported nowhere. Backlog reaches the UI through BacklogDetailModal.vue from the Dashboard instead.

The orders endpoints are untested

There is no test_orders.py, so /api/orders and its four-way filtering — the most filter-sensitive surface in the API — has no coverage. A sample_order fixture already sits unused in conftest.py.
